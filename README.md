# Brazil's Degradation Module

## About

Welcome to the Degradation Driver Layers repository for the [MapBiomas Degradation Module](https://plataforma.brasil.mapbiomas.org/). This repository contains the source code used to generate spatial layers that identify key drivers and structural indicators of native vegetation degradation across Brazil.

The current workflow is organized around MapBiomas Land Cover and Land Use Collection 10.1, using `collectionId = 101`, and produces annual or multi-band outputs up to 2024 depending on the input dataset. Fire-related layers use MapBiomas Fire Collection 4.1. The scripts combine Google Earth Engine processing with auxiliary R/GRASS GIS routines for patch identification, patch size, and morphology calculations.

For a comprehensive overview of the methodology, please refer to the [Algorithm Theoretical Basis Document (ATBD)](https://brasil.mapbiomas.org/). Below, we provide a brief overview of the methodology used to generate each degradation driver layer and the supporting utilities available in this repository.

## Edge area

The edge area layer is generated by the script `01a_fragmentation_edgeArea.js`. The workflow uses annual land cover and land use maps from MapBiomas Collection 10.1 and standardizes native vegetation classes for each biome before calculating edge distance.

Native vegetation classes considered in the current code include Forest Formation, Savanna Formation, Mangrove, Flooded Forest, Wetland, Grassland, and additional native classes represented by class IDs 49 and 50. The script also defines classes that do not generate edge over native vegetation, including Other Non-Forest Formation, Rocky Outcrop, Hypersaline Tidal Flat, and Water.

For each year from 1985 to 2024, anthropic land-use classes are treated as the source of edge effect. The workflow calculates the Euclidean distance from anthropic areas over native vegetation using Google Earth Engine and stores annual bands named `edge_<year>`. The current version calculates distances up to 7 km and exports the output as:

`degradation_edge_area_col101_v2`

## Edge age

The edge age layer is generated by the script `01b_fragmentation_edgeAge_v2.js`. This script uses the edge area output as input, binarizes edge presence, and calculates the number of consecutive years in which each pixel remained under edge influence.

For each year from 1985 to 2024, the age value is incremented when the pixel remains classified as edge and reset to zero when edge influence is absent. The output bands are named `age_<year>`, and the exported asset is:

`degradation_edge_age_col101_v2`

## Native vegetation mask

The script `02a_utils_nativeMask.js` creates an annual native vegetation mask based on MapBiomas Collection 10.1. This mask is used as input for landscape metrics calculated outside Google Earth Engine.

The script groups biome-specific native vegetation classes into a binary native mask for each year from 1985 to 2024 and exports annual bands named `classification_<year>`. The output is stored in the workspace path used by the fragmentation and morphology workflows.

## Export, mosaic, and ingestion utilities

The scripts `02b_utils_exportToBucket.js`, `02c_utils_mosaicTIFF.ipynb`, and `02d_utils_ingestTIFF.R` support the export and ingestion pipeline for rasters that must be processed outside Google Earth Engine.

These utilities are used to export assets to Google Cloud Storage, mosaic GeoTIFF outputs when needed, and ingest processed TIFF files back into Google Earth Engine assets. They are auxiliary scripts and should be adjusted according to the user project, bucket, asset paths, and local processing environment.

## Patch ID and patch size

Patch identification and patch size are produced through a combined Google Earth Engine and R/GRASS GIS workflow:

1. `02a_utils_nativeMask.js` creates the annual native vegetation mask.
2. `02b_utils_exportToBucket.js` exports the mask to Cloud Storage.
3. `03a_fragmentation_id_size.R` processes each annual raster in GRASS GIS.
4. `03b_patchID_uploadToGEE.R` and `03b_patchSize_uploadToGEE.R` ingest the resulting TIFF files back into Google Earth Engine.
5. `03c_patchID_patchSize_formatAsset.js` formats the yearly image collections into multi-band Google Earth Engine assets.

The R script uses GRASS GIS to create binary native vegetation rasters, identify connected fragments with `r.clump`, calculate cell area in hectares, summarize patch area with `r.stats.zonal`, and export patch ID and patch area rasters as GeoTIFF files.

The formatting script exports two public assets:

`degradation_patch_id_col101_v3`

`degradation_patch_size_col101_v3`

The patch ID bands are named `id_<year>`, and the patch size bands are named `size_<year>` for the period 1985 to 2024.

## Patch morphology

Patch morphology is generated by `04a_fragmentation_morphology.R`, ingested by `04b_morphology_uploadToGEE.R`, and formatted by `04c_morphology_formatAsset.js`.

The morphology workflow uses the native vegetation mask and GRASS GIS map algebra to classify native vegetation pixels according to their spatial configuration. The final morphology classes used in the script are:

1. Core
2. Edge
3. Corridor
4. Branch
5. Stepping stone
6. Perforation

The formatted annual Google Earth Engine asset contains bands named `morphology_<year>` from 1985 to 2024 and is exported as:

`degradation_patch_morphology_col101_v2`

## Habitat isolation

Habitat isolation is generated through the scripts `05a_fragmentation_isolation_stepA.js`, `05b_fragmentation_isolation_stepB.js`, `05c_fragmentation_isolation_stepC.js`, and `05d_fragmentation_isolation_stepD_v2.js`.

The workflow is processed at 100 m resolution and uses Collection 10.1 land cover data to create annual natural vegetation masks from 1985 to 2024. In Pantanal, water is included as part of the natural mask in the isolation workflow.

The processing steps are:

1. Create annual natural vegetation masks at 100 m resolution.
2. Calculate connected natural vegetation area using `connectedPixelCount()` with 8-neighbor connectivity and a maximum of 1024 pixels.
3. Define source patches based on three minimum size thresholds: 100 ha, 500 ha, and 1000 ha.
4. Calculate Euclidean distance from source patches up to 25 km.
5. Identify target fragments with maximum sizes of 25 ha, 50 ha, and 100 ha.
6. Classify isolated fragments using distance thresholds greater than 5 km, 10 km, and 20 km from source patches.

The final step exports three isolation assets, one for each source-patch threshold:

`isolation_100ha_col10_v2`

`isolation_500ha_col10_v2`

`isolation_1000ha_col10_v2`

In these outputs, class 10 represents source areas, while classes 1 to 9 represent combinations of target patch size and distance-to-source thresholds.

## Secondary vegetation age

Secondary vegetation age is generated by `06_secondaryVegetation_age.js`. The script uses the MapBiomas deforestation and secondary vegetation product from Collection 10.1 and calculates the age of secondary vegetation from 1987 to 2024.

The script identifies secondary vegetation classes, calculates consecutive years of persistence for each pixel, removes areas interpreted as primary vegetation, and combines the age value with the corresponding land cover class by multiplying the age by 100 and adding the class ID.

The output bands are named `age_<year>` and are exported as a multi-band asset for Collection 10.1.

## Fire age

The fire age layer is generated by `07_fire_age.js`. This script combines MapBiomas Fire Collection 4.1 time-after-fire data with native vegetation classes from MapBiomas Collection 10.1.

The workflow keeps only native vegetation classes, multiplies the fire age value by 100, and adds the land cover class ID. This preserves both the time-after-fire information and the native vegetation class in the same pixel value.

The output asset is:

`degradation-fireAge-col101_v2`

## Fire frequency

The fire frequency layer is generated by `07_fire_frequency.js`. This script combines MapBiomas Fire Collection 4.1 fire frequency data with native vegetation classes from MapBiomas Collection 10.1.

The workflow keeps native vegetation classes, multiplies fire frequency by 100, and adds the land cover class ID. The resulting output stores both fire recurrence information and the associated native vegetation class.

The output asset is:

`degradation-fireFrequency-col101_v2`

## Repository structure

The main scripts are organized by processing step:

* `01a_fragmentation_edgeArea.js`: edge area calculation.
* `01b_fragmentation_edgeAge_v2.js`: consecutive edge age calculation.
* `02a_utils_nativeMask.js`: annual native vegetation mask.
* `02b_utils_exportToBucket.js`: export utility for Google Cloud Storage.
* `02c_utils_mosaicTIFF.ipynb`: TIFF mosaic utility.
* `02d_utils_ingestTIFF.R`: TIFF ingestion utility.
* `03a_fragmentation_id_size.R`: patch ID and patch size calculation in GRASS GIS.
* `03b_patchID_uploadToGEE.R`: patch ID ingestion to Google Earth Engine.
* `03b_patchSize_uploadToGEE.R`: patch size ingestion to Google Earth Engine.
* `03c_patchID_patchSize_formatAsset.js`: patch ID and size asset formatting.
* `04a_fragmentation_morphology.R`: patch morphology calculation in GRASS GIS.
* `04b_morphology_uploadToGEE.R`: morphology ingestion to Google Earth Engine.
* `04c_morphology_formatAsset.js`: morphology asset formatting.
* `05a_fragmentation_isolation_stepA.js`: natural vegetation mask for isolation.
* `05b_fragmentation_isolation_stepB.js`: connected area calculation for isolation.
* `05c_fragmentation_isolation_stepC.js`: source patch and distance layers.
* `05d_fragmentation_isolation_stepD_v2.js`: final isolation classification.
* `06_secondaryVegetation_age.js`: secondary vegetation age.
* `07_fire_age.js`: fire age crossed with native vegetation.
* `07_fire_frequency.js`: fire frequency crossed with native vegetation.

Additional folders such as `Legal_Amazon`, `old`, and `utils` contain complementary, archived, or auxiliary scripts and should be reviewed before reuse.

## How to Run

Most JavaScript scripts are designed to be executed in the [Google Earth Engine Code Editor](https://code.earthengine.google.com/). To run them:

1. Open the Earth Engine Code Editor.
2. Copy and paste the desired `*.js` script.
3. Check input asset paths, output asset paths, version numbers, and processing years.
4. Adjust export parameters such as `assetId`, `description`, `region`, `scale`, and `maxPixels` when needed.
5. Run the script and start the export tasks.

The R scripts require a local environment with R, GRASS GIS, and the required R packages. The upload scripts also require access to Google Earth Engine, Google Cloud Storage, `rgee`, `jsonlite`, and command-line tools such as `gsutil` and `earthengine`.

Example execution for the annual patch ID and patch size workflow:

```bash
parallel -j 12 Rscript 03a_fragmentation_id_size.R ::: $(seq 1985 2024)
```

Before running ingestion scripts, confirm the local TIFF directory, Google Cloud Storage bucket, prefix, target asset collection, manifest directory, pyramiding policy, and overwrite settings.
